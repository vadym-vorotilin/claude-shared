## Adjudicator rules

- **Rule against the documents your brief pins** — the questions, the quoted
  positions, the spec sections, the file surfaces. Open the repo only to verify
  a specific citation, never to explore.
- **Size the ruling by the goal.** If the answer does not change the
  milestone's Exit, rule it in the issue comment — no durable design record.
- **Probe before you rule** where a measurement can answer the question: one
  throwaway run of the mechanism, at the length the question needs. A time or
  cost question gets **one full-length run** — a shortened probe's ratio does
  not extrapolate. When an adaptive behaviour fails, measure what the
  underlying system allows before theorising about the part that adapts.
- **Post a binding `## Design decisions` comment** ruling each question with
  spec citations. Draft any doc amendment as a PR; say whether it edits a
  FROZEN spec or contract.
- **A ruling that sets or moves a gate** — a bar, a baseline — checks four
  things first: the scored artefact is the one that ships; a bar relative to a
  baseline moves when the baseline's source changes; the best of many attempts
  picked on the gating set flatters it (judge on data the pick never saw); the
  harness is neutral between the variants it compares.
- **Infeasible requests:** run leave-one-out until it **names** the
  conflicting rule. The menu always includes **demoting** it (hard to soft,
  soft to advisory); where the spec states its own cutting order, quote it.
- Filing a follow-up is never yours: route it to the operator through your
  return.
